解释：
- 这些是高配电脑上的编辑器短采样，平均约60FPS受限帧影响。p95接近19ms，不能写成“全程稳定60帧”或据此承诺低配表现。
- CPU数值来自CPU Main Thread Frame Time计数器；Main Thread计数还包含等待，不能混用。没有取得可用于下结论的独立GPU耗时。
- DrawCalls来自UnityStats，三角形为渲染计数，可能包含多次渲染/阴影等，不能当作场景独立模型面数。
- 当前数据没有显示规则计算是首要瓶颈。正式关全动物Evaluate约0.005–0.018ms/次；Clone约0.008–0.014ms/次；Clone+Tick约0.013–0.031ms/次。旧荒岛Clone+Tick约0.155ms/次。只是本机热运行微基准，不代表加载/复杂交互峰值。
- 本次Batches/Draw Calls Recorder始终为0，与UnityStats不符，不采用。GetAllocatedBytesForCurrentThread返回值全为0，不把它解释为零分配。GC Allocated In Frame包含编辑器/诊断开销，也不归因于游戏代码。
- Profiler.GetRuntimeMemorySizeLong及Total Used Memory不是独占显存或成品内存；不把编辑器中约5GB总内存写成游戏包的内存要求。

3. 性能优化，按收益证据与风险排序

3.1 首选：治理GLB内嵌未压缩贴图【本轮运行时确认】
第一关活动材质引用15张Texture2D，其中8张4K ARGB32、2张4K RGB24；第四/第五关各20张，其中10张4K ARGB32、4张4K RGB24；旧荒岛22张，其中12张4K ARGB32、4张4K RGB24。
第四关未压缩ARGB32来自木船、码头金属粗糙图、背篓、虾、老板和主角。不是只看磁盘文件大小，而是运行中材质实际引用。
方案第一步：保留原GLB，提取/复用颜色与金属粗糙贴图，先保持尺寸，Windows使用BC7、mipmap开、Read/Write关，颜色sRGB，金属粗糙Linear；通过Unity API重绑定现有材质，保留GUID、UV及shader。第二步再试金属粗糙2K/1K，依据近景A/B决定。
4K ARGB32完整mip链理论约85.3MiB，BC7约21.3MiB，是格式数据量约1/4，不是本轮实测节省显存。RGB24的GPU占用不能简单按3字节/像素推断。
不能把金属粗糙图全部删成常量：像素检查确认粗糙度有明显变化，虾金属度也明显变化。
已有船/老板外置金属粗糙PNG的meta为sRGBTexture:1，且目前没被活动材质使用；接入前应改Linear，不能把它们当作当前画面异常的既定原因。
资源重建脚本会CopySerialized原材质，必须同步纹理映射，否则重建会覆盖优化。
验收：默认视角、最近缩放、剧情近景的颜色/高光/透明边缘不变；重新打开及干净构建后实际纹理格式仍正确；复查构建依赖和加载峰值。
优先于LOD：不动网格、蒙皮与动画，风险更可控。码头8K基色已经BC7，不作为第一刀，也无需继续超分。
资料：Unity 6000.6 BC7文档 https://docs.unity.com/en-us/engine/6000.6/script-reference/unityengine/textureformat/bc7
格式对照 https://docs.unity.com/en-us/engine/6000.0/manual/materials-and-shaders/textures/textures-getting-started/texture-compression-formats/texture-formats-reference

3.2 建立画质基线，减少叠加的渲染成本【配置确认，收益待A/B】
PC_RPAsset为renderScale1.25、MSAA4；相机另有High SMAA；SSAO全分辨率、4级联高质量软阴影。
1.25倍宽高等于1.5625倍像素数，这不是FPS损失百分比。
方案：保留当前高画质档，新增性能基线：100%渲染；比较仅MSAA4或仅SMAA；再单独比较SSAO半分辨率和2级联阴影。一次只变一组，记录GPU/CPU耗时与p95，确认瓶颈才决定默认档。
验收：鱼竿、篓丝、栏杆、模型边缘不明显闪烁；人物接地阴影仍清楚。目标硬件未确定前不承诺提速幅度。
证据：Assets/Settings/PC_RPAsset.asset:28；PC_Renderer.asset:76；Scenes/HabitatIsland.unity:292。

3.3 模型与动画分级【资源确认，建议在贴图之后】
金鱼35,543、寄居蟹36,645、虾30,252、水母22,662三角；活动场景未找到LODGroup。第四关779个活动Renderer对象，5个有效蒙皮网格；Renderer数不是可见DrawCalls数。

31个独立.anim未压缩；水母Idle源文本约5.79MiB，不等于运行内存。精简恒定曲线和冗余关键帧，试30Hz姿态采样并检查循环接缝、握持和离壳。
多个Animator AlwaysAnimate、SkinnedMeshRenderer.updateWhenOffscreen=true。远处或屏外降低姿态采样频率，但动作计时与完成状态要独立可靠，不能简单关Animator导致卡住动作到位或重复结算。

3.4 避免不变状态的重复计算【代码确认，当前非首要瓶颈】
Game空闲时仍逐帧CompleteHabitat；规则Evaluate多次Flood，新建列表/队列/HashSet。HUD已有0.12秒节流，View覆盖层已有0.2秒节流，不能误称全部逐帧重建。
方案：增加状态修订号，水域连通分区只在地形/箱子/潮位等变化时重建；居民报告在相关动物位置/持有/规则变化时失效；UI复用报告、内容变化才赋值。候选状态与已提交状态使用不同缓存标识。
遮挡LateUpdate每帧遍历地块bounds，可缓存静态bounds，只在相机/角色/选中目标/地形变化时重算目标集合，正在淡入淡出的部分仍逐帧更新。
不要直接删除MaterialPropertyBlock：它承担淡化与颜色；若研究SRP批处理，先用Frame Debugger确定批次拆分原因。
验收：动作候选、撤销、潮汐、换岛、读档后报告及时更新；不恢复大面积透明；比较真实Player中的GC.Alloc/CPU耗时。
证据：Scripts/HabitatGame.cs:100；HabitatModel.cs:165,209；HabitatHud.cs:233；HabitatView.cs:1519；HabitatOcclusionFade.cs:187。
Unity批处理方法选择：https://docs.unity.com/en-us/engine/6000.6/manual/analysis/graphics-performance-profiling/reduce-draw-calls/optimizing-draw-calls-choose-method

3.5 碰撞、重建与撤销内存【代码确认，收益待测】
码头MeshCollider直接复用约38,260三角渲染网格；行走持续采样地面。制作仅甲板/栈桥/合法坡面的低面碰撞体，保持已测行走轮廓，不再包含屋顶/植物装饰；先不改美术模型。

4. 操纵手感优化

4.1 单步输入缓冲【代码确认问题入口，参数属试调】
Busy在HandleInput开头直接return，约0.4秒行走、0.67秒推拉以及更长工具动作期间的短按会丢失，暂停/镜头输入也被挡在外面。
建议动作尾部只缓存最后一次移动方向，初试100–150ms；不排长队。相机与安全暂停从状态修改输入中分离。执行下一步仍须前一步视觉到位、校验成功后提交。
验收：30/60/120fps快速转向与连续走格；取消/读档/换岛清空缓存；不出现多走一格、提前扣道具或重复结算。

4.2 快捷键与方向意图【代码确认】
8种工具仅有1–5快捷键，补6–8与现有预览/确认一致；不要选中就消耗。
方向同时按下时当前固定W/S/A/D优先级，可改为最后按下的方向优先，配合单步缓冲测试。
长期再做可重绑定/手柄InputActions，初版前不宜整体迁移输入系统。

4.3 相机旋转过渡【体验建议】

输入方向必须根据明确目标朝向映射，不随插值中间角度变；保留已确认48度俯角/14度基础偏航。

4.4 水母诱导的到位一致性【代码风险，需专项复现】
Lure通过Mutate立即改动物坐标，View随后插值；通关会等待居民到位，但重复诱导是否可在视觉未到位时沿新逻辑位置继续操作，值得补测。

验收：连续快速诱导、撤销、取消、读档不出现视觉与可操作位置分离。这一条本轮未用真实鼠标复现，不冒称已发生的玩家bug。
证据：Scripts/HabitatGame.cs:495；HabitatModel.cs:583；HabitatView.cs:1466。

4.5 真人难度与路线理解【体验建议】
既有全主线是控制器自动回归，证明可行，不能证明新玩家操作轻松。钓鱼自动控制器不是人工手感验收。
安排3–5位未玩过的测试者，记录首次理解耗时、钓鱼成功率、误操作、无法判断下一步的位置，再调整难度。
第二关现有已验证路线收南岸后需返码头重新上岸取北岸鱼，可考虑可见回程路线或明确收尾顺序；不能仅因这条路线绕就声称地图没有任何其他解。

6. 推荐实施批次与验收门槛

第一批：重开物资保护、重开防误触、右键有效目标校验、失焦暂停；同时补存档候选校验/备份恢复。每项独立回归，维持已有玩法规则与UI布局。
第二批：GLB贴图等尺寸压缩与重建流程绑定；再做100%渲染/抗锯齿配置A/B。保留原资源与可回退配置。
第三批：单步输入缓冲、6–8快捷键、诱导到位专项验证；逐项确认手感与取消行为，不一并大改输入架构。
第四批：全图构图、材质关系、接触反馈；再按真实Player剖析结果决定LOD、动画采样、缓存/对象池。
发布前：更新过时Player烟测，执行最新构建的启动/退出/读档/五关流程；使用目标中档电脑测CPU/GPU帧时、p95、加载峰值、内存稳定性；人工试玩不由自动回归替代。
暂缓：大规模规则重写、输入系统全面迁移、全部资源重新减面、全项目一刀切降清晰度。当前采样没有证据证明这些是最有价值的第一步。
